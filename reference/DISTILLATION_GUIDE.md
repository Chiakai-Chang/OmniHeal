# OmniHeal 參考研究指南 (Research & Distillation Guide)
> 版本：v1.0 | 適用對象：負責研究外部 repo 並優化本專案的 AI 代理

本文件定義了當使用者提供外部 GitHub repo 連結時，AI 代理應如何有系統地研究、評估、並將有價值的設計導入 OmniHeal，同時確保本 repo 保持乾淨、不受汙染。

---

## 核心原則：智慧萃取，而非盲目搬運

我們追求的是「邏輯的精煉」，不是「功能的複製貼上」。

- **價值優先**：導入的唯一理由是該設計能讓 OmniHeal 更好用、更穩健、或覆蓋更多場景
- **高保真萃取**：一旦決定導入某個想法，必須確保其核心邏輯完整，而非殘廢式的閹割版
- **果斷放棄**：如果一個設計讓 OmniHeal 變臃腫、難維護、或偏離「AI 代理指令手冊」的定位，直接略過
- **維護性優先**：優先採用能持續跟進上游的整合方式（如 submodule），而非一次性快照

---

## 研究流程 SOP

### 第一步：隔離 Clone（執行前必看）

```bash
# 在 OmniHeal 根目錄下操作
git clone <使用者提供的 repo URL> research/<repo名稱>/
```

**確認 `.gitignore` 包含 `research/`，確保研究素材不會被提交到本 repo。**

若 `.gitignore` 尚未設定，立即補上：
```
research/
```

---

### 第二步：戰略評估（SWOT）

閱讀 clone 回來的 repo 後，針對 OmniHeal 進行分析：

| 面向 | 問題 |
|------|------|
| **優勢 (S)** | 這個 repo 有什麼是 OmniHeal 目前缺少的？對哪個場景特別有用？ |
| **劣勢 (W)** | 導入它的代價是什麼？會讓 OmniHeal 更複雜嗎？ |
| **機會 (O)** | 它是否能補強 OmniHeal 的某個弱點（如：Phase 0 問答設計、報告格式）？ |
| **威脅 (T)** | 它的設計假設是否與 OmniHeal「Agent 本身就是 LLM」的核心模型衝突？ |

---

### 第三步：決策矩陣（TOWS）

根據 SWOT 推演最適的導入路徑：

| 策略 | 條件 | 行動 |
|------|------|------|
| **SO** | 設計強大且結構相容 | 直接以 `git submodule` 引入，或大比例採用其架構 |
| **WO** | 設計有價值但過於龐大 | 只萃取核心 Prompt 邏輯或流程概念，改寫進 OmniHeal 的 phases/ 或 skills/ |
| **ST** | 設計好但更新頻繁不穩 | 以快照方式導入，標記為「參考自 X repo」，不追蹤上游 |
| **WT** | 代價高於收益 | **果斷放棄**，記錄原因即可 |

---

### 第四步：導入目標對照表

評估後，將有價值的設計對應到 OmniHeal 的具體文件：

| 外部設計 | 可能影響的 OmniHeal 文件 |
|---------|------------------------|
| 更好的目錄掃描邏輯 | `src/probe.py` |
| 更精良的 Prompt 框架 | `skills/skill_*.md` |
| Phase 0 互動問答設計 | `phases/phase0_bootstrap.md` |
| 報告格式設計 | `phases/phase1_scanner.md` 的輸出規格 |
| 治理規則文件結構 | `templates/constitution_base.md` |
| 整體工作流程優化 | `LAUNCH.md` 或 spec 文件 |

---

### 第五步：執行導入 + 更新 Spec

確認導入路徑後：

1. 修改對應的 OmniHeal 文件（phases/、skills/、templates/、LAUNCH.md）
2. 若影響整體架構設計，同步更新 `docs/superpowers/specs/` 下的設計文件
3. 在 `reference/RATIONALE.md` 記錄：
   - 參考了哪個 repo 的哪個設計
   - 為什麼選擇導入（或放棄）
   - 做了哪些調整以符合 OmniHeal 的架構

---

### 第六步：驗收檢查

導入完成後自我檢核：

- [ ] 導入的設計是否讓 OmniHeal 更容易被 Agent 理解並執行？
- [ ] 是否維持「使用者說一句話，Agent 全自動處理」的核心體驗？
- [ ] 新增的複雜度是否值得？（若不確定，先不加）
- [ ] `research/` 是否確實在 gitignore 中，沒有汙染本 repo？
- [ ] 相關文件是否已同步更新？

---

## 嚴禁行為

- **嚴禁** 將 research/ 裡的原始碼直接複製進本 repo
- **嚴禁** 引入讓使用者需要手動安裝額外工具才能運行的依賴
- **嚴禁** 因為「某個設計很酷」就導入，必須有明確的 OmniHeal 使用場景
- **嚴禁** 導入後不記錄來源與理由（黑箱操作）

---

## 快速參考：OmniHeal 的核心設計約束

在評估任何外部設計時，必須確保不違反以下約束：

1. **Agent 就是 LLM**：OmniHeal 不需要也不應該呼叫第二個 AI 模型
2. **零安裝啟動**：使用者 git clone 後，只需對 Agent 說一句話即可啟動全流程
3. **領域無關**：設計必須對程式碼、日誌、文字稿等不同類型的內容都適用
4. **永不中斷**：錯誤必須被記錄後跳過，絕對不允許中斷整個掃描流程
5. **進度可見**：所有執行結果寫入 `progress/`，人眼可讀
